# 2026-08-13 — Client change list H4 and H7: meals, and the milestone that followed the wrong streak

Both items originate in the iOS repo (`genesxy_apple.V1.02`), which is the shared-backend repo and
holds the executable copy of every migration. Android's brief for this batch was **read parity**:
identical backend rows must produce identical numbers on both phones. Nothing automated detects
divergence between the two clients, so each of these changes was made in the same sitting as its iOS
counterpart, and each carries a dated comment saying so.

**No SQL was written or run for either item.** `daily_logs.food_groups` was already live.

## H4 — `food_groups` reaches Android (read/write half)

**State: WORKING** (`:app:testDebugUnitTest` green; `DailyLogMigrationTest` green on emulator)

**Why it mattered.** iOS was about to start counting food groups toward the streak. Both apps share
one `daily_logs` table, and Android neither stored nor sent that column — so the same account would
have shown a streak of 9 on one phone and 2 on the other, with nothing to explain the gap.

**Changes.**
- `data/local/entity/DailyLogEntity.kt`, `data/local/GenesyxDatabase.kt`,
  `data/local/Migrations.kt` — Room v8 → v9, `MIGRATION_8_9` adding a **nullable** `foodGroups TEXT`
  with no `DEFAULT`. The generated `app/schemas/.../9.json` was checked against the ALTER by hand.
- `data/remote/dto/DailyLogDto.kt` — field omitted while empty, so an Android write can never blank
  a column it has no UI for.
- `data/remote/SupabaseDailyLogRemoteDataSource.kt` — read and write.
- `domain/model/DailyLog.kt`, `domain/model/LogDay.kt` — `isMeaningful()` widened to count meals, the
  same rule iOS applies in `TrackingEngine.isMeaningfulLog` and `StreakEngine.hasAnyEntry`. This is
  the whole point of the item: a meal-only day now holds a streak identically on both clients.

**Two real defects found while doing it, neither of them the feature.**
- `ui/screens/LogScreen.kt` rebuilt the entire row on save. Once iOS started writing meals, every
  Android save would have **silently deleted them** — a data-loss bug that would have looked like an
  iOS sync fault. The form now carries them through.
- `data/DailyLogRepository.kt` — `upsertPreservingWater` protects the same columns against a sync
  landing mid-edit.
- Meal-only days rendered as empty in Android history. Fixed.

**Vectors.** `domain/tracking/tracking_test_vectors.json` was extended. The long-standing claim that
this file mirrors the iOS one byte-for-byte **was never true and never had been** — the two use
different schemas. That claim is now corrected in both repos and each file was extended in its own
schema. The additions were falsification-tested: removing the predicate term makes
`TrackingVectorTest` fail.

**Migration test.** `androidTest/.../DailyLogMigrationTest.kt` gained a v8 → v9 case. Every prior
`daily_logs` migration had one and this did not. It runs on a real emulator and fails if the ALTER
grows a `DEFAULT`.

**Still owed on Android:** a food-group control. There is still no way to *record* a meal here —
Android reads and syncs them only. iOS closed its half the same day (a toggle section in the day-log
sheet, plus the additive recipe path). Also owed: offline / relaunch / sync QA on a device.

## H7 — the daily milestones now follow the streak she is shown

**State: WORKING** (`:app:testDebugUnitTest` — 381 tests, 0 failures, 0 skipped)

**Diagnosis.** `domain/streaks/StreakEngine.kt` earned `DAY_7`/`DAY_14` off `dailyHydration`, while
`HomeScreen` headlines `dailyActivity`. A woman who logged a meal and her symptoms every day for a
fortnight watched the streak on her Home screen climb past 14 and was congratulated for nothing,
because she had not logged water. Hydration has its own number and its own tile; it was quietly
holding a badge earned by a streak it does not represent. The weekly pair (`WEEK_1`, `WEEK_4`) were
always activity-based, so the two halves of the same feature disagreed with each other.

**Changes.**
- `domain/streaks/StreakEngine.kt` — `DAY_7`/`DAY_14` now key off `dailyActivity`. Water still
  counts: a day with water on it is an active day. Comment records the cross-platform contract and
  the date.
- `ui/home/HomeScreen.kt` — the two labels read "7 / 14 days of logging in a row", not "of
  hydration". They now arrive for a week with no water logged in it at all, and the old wording
  would have been wrong.
- `test/.../StreakEngineTest.kt` — one test, written **first** and watched fail
  (`AssertionError at StreakEngineTest.kt:234`) before the engine was touched: seven meal-only days
  must give `dailyHydration == 0`, `dailyActivity == 7`, and `DAY_7` earned.

**Android needed no celebration UI.** `HomeScreen.MilestoneDialog` already existed and already fired
without notification permission. iOS was the platform missing that entirely — its milestone check sat
inside `replan()` behind `guard isActive`, so on iOS the whole feature existed only for users who had
granted notification permission. That is fixed on the iOS side; see `docs/HANDOFF.md` §4p there.

**One cosmetic divergence, recorded rather than hidden.** Android's dialog lists *every* newly earned
milestone at once ("Milestones reached", plural). iOS shows only the largest, on the reasoning that
crossing `DAY_7` and `WEEK_1` in the same moment is one good week and not two stacked modals. The
numbers agree, which is the contract that matters; the presentation does not. Worth settling when
someone owns the moment as a design question.

**Still owed (both clients, product decision):** streak *restore*. It changes what a streak means and
could become a paid entitlement, so grace and allowance need approving before either app implements
it. Backend state only if a restore must follow the account across devices.

## Carried constraints

- **This repo must not grow a `supabase/migrations/` directory.** One executable copy of each
  migration lives in the iOS/shared-backend repo; `docs/migrations/` here holds audit pointers only.
- Gradle needs `JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"` on this
  machine — `/usr/libexec/java_home -V` finds nothing.
- **Settled the same day, and Android was already right.** A logged **zero-hour sleep** counted as a
  meaningful entry under both Android predicates (`domain/model/DailyLog.kt:57`,
  `domain/model/LogDay.kt:17`) and under iOS `StreakEngine.hasAnyEntry` — all `!= null` — but not
  under iOS `TrackingEngine.isMeaningfulLog`, which read `> 0`. One implementation of four,
  disagreeing with the shared rule the vectors have recorded since v2. iOS has been brought in line;
  **no Android change was needed or made.** Do not "correct" these two predicates to `> 0` — they
  are the reference.
