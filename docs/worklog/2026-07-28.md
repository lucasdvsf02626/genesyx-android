# 2026-07-28 — Bug-fix batch: single source of truth (device-walkthrough findings)

Batch theme: cross-screen data inconsistencies from the 28 Jul device walkthrough — cycle phase,
hydration total, sleep, and pH "latest" disagreeing between screens. Fixed phase by phase; each
phase committed with tests green.

## Phase A — Cycle (Bugs 1 + 2, groundwork for 9)

**State: WORKING** (`:app:testDebugUnitTest` green after phase)

**Diagnosis.** There is exactly one phase algorithm (`domain/cycle/CycleEngine.getCyclePhase`) —
no duplicate implementations. Both bugs were divergent *inputs*:

- `CycleSettingsDialog` seeded its stepper state via un-keyed `remember`, so the modal froze on
  whatever `current` was at first composition. `CycleRepository.settings` is a StateFlow that starts
  `null` and emits the real row a beat later — the modal could show defaults/stale values (33) while
  the card behind it rendered the persisted row (32). One day of cycle length moves the ovulation
  day (`cycleLength − 14`) and flips day 19 between Luteal (32d) and Ovulatory (33d) — exactly the
  observed Bug 1.
- `HomeScreen` kept a remembered `cycleSeed` snapshot that took priority over live state and was
  never cleared after save/dismiss.
- `TrackScreen`/`CycleDetailScreen` captured `remember { LocalDate.now() }` (frozen past midnight),
  and `CycleDetailScreen` computed its prediction card via `OvulationLogic.compute(settings)`
  without passing the same `today` as its phase card.

**Changes.**
- `ui/components/CycleSettingsDialog.kt` — stepper/date state now keyed on `current`
  (`remember(current)`), so the dialog re-seeds from the latest repository emission.
- `ui/home/HomeScreen.kt` — `cycleSeed` now used only by the first-run card (which hands over a
  freshly picked date); menu/hero entry points pass live `state.settings`; seed cleared on
  save/dismiss.
- `ui/track/detail/CycleDetailScreen.kt` — un-remembered `today`; prediction card now shares the
  phase card's `today` (`OvulationLogic.compute(settings, today)`).
- `ui/track/TrackScreen.kt` — un-remembered `today`.
- No `CycleCalculator` extraction: `CycleEngine` already is the single pure
  settings + date → phase/ovulation/fertile-window function and every screen already calls it.
  Extracting a rename would have been a rewrite without a behaviour change.

**Tests / vectors.**
- `CycleEngineTest` — new boundary pins: period→follicular adjacency; ovulation day / day-after on a
  32-day cycle; the 32-vs-33 day-19 Luteal↔Ovulatory flip (walkthrough repro).
- `tracking_test_vectors.json` — new **additive** top-level `cycleCases` section (8 vectors: the
  walkthrough repro pair, ovulation-day and day-after boundaries, first/last period day, first
  follicular day, fertile-window open boundary). `spec` stays `genesyx-tracking-v1` — no existing
  case or metric changed semantics. `TrackingVectorTest` extended to run them against `CycleEngine`.
- **iOS pickup:** the mirrored vector file gains `cycleCases`; the iOS runner needs a matching
  cycle-vector test (schema documented in the file's `note`). Existing streak cases untouched.

**Remaining (noted, not fixed here).** `NutritionViewModel`/`HomeViewModel` evaluate
`LocalDate.now()` inside their combine lambdas, so a screen left open across midnight still shows
yesterday's phase until the next emission — a full fix needs a date ticker, out of scope for this
batch. Cycle-settings offline retry gap (`CycleRepository.upsert` fire-and-forget) unchanged, as
already documented in CLAUDE.md.

## Phase B — Hydration single source of truth (Bug 3)

**State: WORKING** (`:app:testDebugUnitTest` + androidTest compilation green after phase)

**Diagnosis.** There is exactly one persisted value (`daily_logs.waterMl`) — no second store, so no
new `HydrationRepository` was needed; `DailyLogRepository.logByDate` already is the shared aggregate
and every surface already collects it. The four simultaneous values came from three write/read
defects around that single column:

1. **Log Today clobber (the 1.8 L).** `LogScreen` snapshotted `waterMl` into un-keyed `remember`
   at open and "Save log" wrote the whole row from that snapshot — reverting any quick-add made
   while the form sat open, and making the form's stale number the new truth.
2. **Nutrition out-of-band read (the 0.0 L).** `NutritionViewModel` discarded the emitted logs and
   side-read `waterMlOn(today)` (`.value`), rendering its `initialValue` (0) until its own combine
   emitted.
3. **Quick-add lost updates.** `adjustWater`/`setWater` did read-modify-write against the in-memory
   StateFlow snapshot; two rapid taps both read the pre-write value and the second overwrote the
   first. `SleepDetailViewModel.setSleep` had the same full-row snapshot hazard (could clobber
   water from the sleep screen).

**Changes.**
- `data/DailyLogRepository.kt` — new private `mutateRow(date, transform)`: mutex-serialized
  read-modify-write against the DAO row (push kept outside the lock). `adjustWater`/`setWater` now
  route through it; new `setSleep` and `upsertPreservingWater` (form save that keeps the stored
  row's water). Plain `upsert` unchanged for full-row callers.
- `ui/screens/LogViewModel.kt` — `todayWaterMl` StateFlow (live aggregate), `setWater`
  write-through; `save` → `upsertPreservingWater`.
- `ui/screens/LogScreen.kt` — Water mini-card renders the live aggregate; `WaterDialog` Done writes
  through the repository immediately (so every screen updates at once); water excluded from the
  dirty/discard check since it is no longer form state.
- `ui/nutrition/NutritionViewModel.kt` — hydration read from the emitted `logs` map.
- `ui/track/detail/SleepDetailScreen.kt` — `setSleep` delegates to the repository method.

**Behaviour note:** water entered via the Log Today dialog now persists on "Done" rather than on
"Save log" — it is tracker data, not form state, so "Discard changes" no longer reverts it.

**Tests.** Instrumented `DailyLogRepositoryTest` gains `rapid_quick_adds_all_land` (5×+200 → 1000)
and `form_save_preserves_water_quick_added_while_the_form_was_open`. These need a device run
(`connectedDebugAndroidTest`) — compiled green here, execution pending the end-of-batch sweep.

**Known remaining (unchanged, pre-existing):** the cold-start window where `SessionRepository.userId`
is still null can file a write under the guest bucket for a signed-in user (row split across
userIds); guest daily logs are not adopted on sign-in (pH has `adoptGuestReadings`, daily logs
don't). Both predate this batch — flagged for a follow-up, not touched here.

## Phase C — Sleep editor shows the saved night (Bug 4)

**State: WORKING** (`:app:testDebugUnitTest` green after phase)

**Diagnosis.** Three stacked problems on `SleepDetailScreen`:
1. `todayMinutes` collapsed null (no entry) to 0 at the state boundary, and the editor seeded its
   draft with **no `loaded` gate** — before Room's first emission the stepper showed "0h 0m" over a
   real entry. The observed "LAST NIGHT 1h 15m" was the user rebuilding their night on that phantom
   zero (steppers are +60/+15).
2. The "This week" card is ISO Mon–Sun (`SleepInsightLogic`) while the Track row is a rolling last-7
   window ("most recent night") — an entry filed on Sunday shows in Track on Monday but not in the
   new ISO week. Labels are honest on both, so the windows are kept as-is; the real defect was (1).
3. Save was already an upsert on (user, date) — "second record" was never possible; confirmed, no
   change needed there.

**Changes.**
- `ui/track/detail/SleepDetailScreen.kt` — `SleepDetailState` gains `loaded`; `todayMinutes` is now
  `Int?` (null = no entry, distinct from a saved 0). The editor card only composes once `loaded`,
  and the draft seeds from the saved entry (`remember(state.todayMinutes)`), so reopening after
  saving 8h shows "8h 0m". (The write path moved to `DailyLogRepository.setSleep` in Phase B.)
- New `SleepDetailViewModelTest` (5 tests): null-vs-zero, loaded gate, prefill, week-with-a-night
  is not the empty state, write-through.

**Acceptance check (unit-level):** save 8h → `todayMinutes` emits 480 → draft re-seeds to 8h 0m;
a saved night in the current ISO week sets `hasData`, so the week card shows a bar. On-device
confirmation in the end-of-batch sweep.

## Phase D — pH "latest reading" picked by position, not time (Bug 5)

**State: WORKING** (`:app:testDebugUnitTest` green after phase)

**Verification first, as the brief asked.** The Nutrition card does NOT load once in `init` — the
hypothesis was wrong. `PhTrackerSection` collects `PhRepository.readings`, a live Room Flow, so the
card updates on every save. The actual defect: `PhTrackerCard` picked its "latest" with
`readings.lastOrNull()` — the only positional pick in the app (Track and Home both use
`maxByOrNull { it.recordedAt }`). It leaned on the DAO's `ORDER BY recordedAt ASC`, which is a
lexicographic sort over a TEXT column, and a server round-trip can shift `recordedAt` (offset
dropped on parse), reordering rows. That makes "card shows 5.1 while Track shows 5.4" reachable,
matching the screenshot.

**Change.** `ui/components/PhTrackerCard.kt` — `latest = readings.maxByOrNull { it.recordedAt }`,
aligning all three surfaces on the same rule.

**Noted, not touched (pre-existing, out of batch scope):** `PhTrackerSection` discards the
`PhWriteResult`, so an out-of-range write would close the dialog silently (unreachable from the
slider today); the range filter captures `LocalDateTime.now()` inside a `remember` keyed on
readings+range (cutoff goes stale only across midnight with no new readings); pH timestamps drop
the server's UTC offset on parse — the deeper timestamp-normalisation fix belongs with an iOS-parity
pass since it touches wire behaviour.
